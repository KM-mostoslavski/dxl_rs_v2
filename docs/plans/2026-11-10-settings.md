# Typed settings on most models: implementation plan

**Goal:** the typed setters of `2026-11-09-typed-limits.md` (D1 to D10) work on most models, not only the six tables whose unit data is verified, and the remaining common settings get typed setters too: Homing Offset, Moving Threshold, Return Delay Time and the operating mode. Raw access stays for registers a minority of models have (maintainer, 2026-11-10: "raw registers are only for unique capabilities that not most actuators have").

**Spec:** SRS FR-10 (drafted 2026-11-10, reconciled with D1 to D10 by T110). The maintainer delegated every decision below on 2026-11-10 ("take decisions yourself").

**Why the tables:** a typed value needs the register's `unit_info` (scale and e-Manual range, FR-9.2, D6). On 2026-11-10 only 6 of 76 tables carry it (`unit_source`), so on the other 70 every typed limit, and every FR-9 typed read, returns `NoUnit`. Each of those tables is verified against its e-Manual page now, as FR-7.2 asks when a model is first needed.

## Decisions

- **S1. One trait for every setting.** `LimitField` becomes `SettingField` and `ActuatorRef::write_limit` becomes `write_setting`: the trait now carries settings that are not limits. Free: neither name has reached `dev`. Every D1 to D10 rule stays as built (unicast only, `ReadField` but not `WriteField`, D4 checks, D5 cache, D8 torque confirmed off, D9 wheel switch).
- **S2. Three scalar settings.** Fields, setters and getters, built like `TemperatureLimit` (D3, D4, D6), not cached:

  | Field | Registers | Value | Setter / getter |
  |---|---|---|---|
  | `HomingOffset` | Homing Offset | `Position`, an angle offset: converted through the step the `unit_info` gives (`deg`, or `pulse` = one position tick of `type_info`), never through the zero point | `set_homing_offset` / `homing_offset` |
  | `MovingThreshold` | Moving Threshold | `Velocity` | `set_moving_threshold` / `moving_threshold` |
  | `ReturnDelayTime` | Return Delay Time | `core::time::Duration` (`unit: "µs"`, 2 µs per step on every page seen) | `set_return_delay_time` / `return_delay_time` |

  Roles `HomingOffset`, `MovingThreshold`, `ReturnDelayTime` with their `Has*` traits; Tier 2 follows whatever the limits do. Docs: Homing Offset shifts Present Position, the cached position limits stay raw and still apply in the shifted frame; Return Delay Time adds to every reply's latency, so the bus timeout must exceed it.
- **S3. Operating mode setter.** New `#[non_exhaustive] pub enum OperatingMode { Current, Velocity, Position, ExtendedPosition, CurrentBasedPosition, Pwm }` in core beside `LimitMode`, re-exported at the crate root. `ActuatorRef::set_operating_mode(mode: OperatingMode)` and `operating_mode() -> Result<OperatingMode, Error>` (one unicast read, never cached).
  - The raw value comes from the table's `operating_modes` lists: `Position` = the one value of `bounded`; `ExtendedPosition` = the one value of `unbounded` not in `current_position`; `CurrentBasedPosition` = `current_position`; `Current` = `current`; `Velocity` = `velocity`; `Pwm` = `pwm`. No such value, or more than one: new `ValidationError::UnsupportedMode { id, mode }`, nothing sent. A value read back that maps to no named mode: a validation error carrying the raw value (new variant, FR-6.6).
  - Angle-limit models (AX, RX, MX on P1: `ModeSource::AngleLimits`) return `ValidationError::Unsupported { id, register: "Operating Mode" }`; the docs point to `set_position_limits`, which already switches wheel / joint / multi-turn (D5, D9).
  - Checks as every setting: torque confirmed off (D8), the register exists. One acknowledged unicast Write of the register.
  - Cache: a confirmed write records the new limit mode. If the new mode bounds its goal (Velocity: Velocity Limit; Current and CurrentBasedPosition: Current Limit) and the model has that register, the call then makes one unicast Read of it to cache the goal bound, so goals stay checked: this read is part of the method's documented contract. If it fails, the bound is unknown (goals refused, `LimitsUnknown`) and the call returns the read error, the mode already written. A write that fails after bytes went out leaves the mode unknown: every goal is refused until a confirmed `set_operating_mode` or the next Setup.
  - Docs list the side effects the e-Manual gives (X series: gains, Profile Velocity and Profile Acceleration reset, Goal PWM and Goal Current set to their limits; current-based position mode also resets the position gains and PWM Limit), and that a goal register keeps its last value: write the goal before `enable_torque`.
- **S4. Table data for 70 tables.** For each table without `unit_source`, its e-Manual page is read and the table gains `unit_source: Verified(url, verified: "2026-11-10")`, `unit_info` (step, unit, sign type, range and the other FR-9 keys) for every setting register and FR-9 register it has rows for, and on Protocol 2 tables the per-mode `operating_modes` lists. Values from the page only (Principle IV), each group checked again by a second reader. Rows (address, size, name) are not changed: a row the page contradicts is reported in `docs/deferred.md`. Left out: `rh_p12_rn.ron` (D-24 open: its position scale has no e-Manual source) and the `operating_modes` lists of `xl320.ron` (D-17 open).
- **S5. Later, still raw:** ID, baud rate and protocol type (FR-10.6: which ID and rate the reply uses is unconfirmed on hardware), Drive Mode and Shutdown (their bits are not in the tables yet, D-11), Secondary ID (FR-10 out of scope).

## Review focus

- No path writes EEPROM without torque confirmed off, on any tier; settings stay out of `sync_write`, `bulk_write` and the Easy tier at compile time.
- After `set_operating_mode`, every goal is checked exactly as Setup would have recorded that mode, or refused.
- Every step, unit and range in a table comes from the page its `unit_source` cites.
