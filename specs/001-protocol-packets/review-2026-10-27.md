Adversarial review of `src/protocol*` and its `src/error.rs` / `src/lib.rs` edits: two reviewers (correctness; SRS/constitution compliance and fit for the bus), each batch re-checked by a skeptic that tried to refute every finding. ## Confirmed

### protocol-trait-does-not-carry-exchange (high, protocol-compliance)

`src/protocol.rs:86`: The public `Protocol` trait does not imply the crate-private `Exchange` trait. Generic bus code bounded by `P: Protocol` (the FR-1.1 signature) therefore cannot call ping/read/write/sync_write, and adding a `P: Exchange` bound to a public `impl Bus<P, T>` trips the `private_bounds` lint, which CI denies with -D warnings.

**Evidence**: src/protocol.rs:45 `pub trait Protocol: sealed::Sealed { const BROADCAST: u8 = 0xFE; }` and :86 `pub(crate) trait Exchange: Protocol`. The contract (protocol-api.md) says `Protocol` holds `/* crate-internal items */`, and FR-5.1 says the Protocol trait builds and parses packets. A scratch crate with the same shape fails with `impl<P: Protocol> Bus<P> { pub fn a(&self) -> u8 { P::read() } }` -> `error[E0599]: no associated function or constant named read found for type parameter P`. With `impl<P: Protocol + Exchange> Bus<P>` it gives `warning: trait Exchange is more private than the item Bus<P> ... #[warn(private_bounds)] on by default`.

**Fix**: In src/protocol.rs, move `Exchange` (and `Link`, `Pong`, plus the internal `Transport` bound until crate::transport::Transport replaces it) into `mod sealed` as `pub` items. Re-export them with `pub(crate) use sealed::{Exchange, Link, Pong};` and declare `pub trait Protocol: sealed::Sealed + sealed::Exchange { const BROADCAST: u8 = 0xFE; }`. Then update contracts/protocol-api.md so `Exchange` is a sealed supertrait of `Protocol`.

**Skeptic (confirmed)**: I reproduced this with rustc 1.97.1 in a scratch crate shaped like this code: `pub trait Protocol: sealed::Sealed`, `pub(crate) trait Exchange: Protocol`, `pub struct Bus<P>`. `impl<P: Exchange> Bus<P> { pub fn a(..) }` gives `warning: trait Exchange is more private than the item Bus<P>` (private_bounds is on by default, and CI runs with -D warnings). `impl<P: Protocol>` cannot call `P::read`. research.md:109 already notes that `pub(crate) trait Sealed` trips private_bounds, but that reasoning was not applied to Exchange. So the FR-1.1 shape `Bus<P: Protocol, ..>` cannot use the exchange API without a lint allow. The proposed fix works: I put `Exchange` and `Link` as `pub` items inside the private `sealed` module, made `Protocol: sealed::Sealed + sealed::Exchange`, and ran `impl<P: Protocol> Bus<P>` calling `P::read(&mut Link{..})`. It is clean under cargo clippy, with no private_bounds or private_interfaces warnings.

### alert-discards-read-data (medium, protocol-correctness)

`src/protocol.rs:232`: `check` returns `Err(StatusError)` for any non-zero error byte before it checks the length, and the reply data is never given back. While a P2 alert (or a persistent P1 Overheating/Overload flag) is set, no register can be read, including Hardware Error Status (70), the register the e-Manual says to read to diagnose the alert.

**Evidence**: protocol.rs:232 `if status.error != 0 { return Err(StatusError {..}) }` runs before `if status.len != len`. Scratch test: reply `packet(1, STATUS, &[0x80, 0x20])` to `P2::read(.., id(1), 70, &mut out)` gives `Err(Status(StatusError { id: Id(1), report: P2 { alert: true, code: None } })) out=[32]`. The data arrived, but the API gives no valid way to use it. The XM430 e-Manual says: "Check Alert Bit(0x80) in an error field of Status Packet or a present status via Hardware Error Status(70)". The alert stays latched until reboot, so that read can never succeed. sync_read has the same problem: `on_reply(id, check::<P2>(..).map(|()| &*buf))` drops the data for any ID whose reply is in alert.

**Fix**: Keep the Err, as FR-6.2 and G6 require, but make the data usable. In protocol.rs `check`, test the ID first, then the length, then the error byte. Then document on `Exchange::read` (and P1 read) that when it returns `Error::Status` and the reply carried exactly `out.len()` bytes, `out` holds that reply. Add a test: read addr 70 with the 0x80 error byte, expect Err(Status{alert:true}) and out == [0x20]. For sync_read, either leave it as a known limit or later pass the data with the status error (e.g. `Result<&[u8], (Error, Option<&[u8]>)>`). That second change touches the contract, so it is the architect's call.

**Skeptic (confirmed)**: I reproduced it on a scratch copy. Replying packet(1, 0x55, [0x80, 0x20]) to P2::read(id 1, addr 70, out[1]) gives Err(Status(StatusError { id: Id(1), report: P2 { alert: true, code: None } })) with out=[32]. The data lands in `out`, but the contract does not promise that, and check() tests the error byte before the length, so on Err `out` may not hold a full reply. Returning Err on alert is what SRS FR-6.2 and G6 require, so 'treat alert as Ok' would break the spec and is rejected. The real defect is narrower. The e-Manual says to diagnose an alert by reading Hardware Error Status (70), and FR-6.5 clear_fault() re-reads it. While the alert is latched, every read returns Err, so the API cannot say which fault (overload, overheat, voltage) is behind it. In sync_read the callback only gets Err, so the data is lost there too.

### p2-unbounded-len-swallows-replies (medium, protocol-correctness)

`src/protocol/p2.rs:239`: The P2 status parser accepts any LEN up to 0xFFFF. One bit flip in LEN_H makes it keep reading bytes until the deadline, so the replies that follow are lost and the result is a timeout instead of a resync. In sync_read, the next actuator's valid reply is lost.

**Evidence**: p2.rs:239-245 `self.remaining = usize::from(u16::from_le_bytes([self.len_l, byte])); if self.remaining < 3 { malformed } else { State::Instruction }`. There is no upper bound related to `out.len()`. Scratch test: READ_REPLY_1 with `bad[6] ^= 0x80`, then a valid READ_REPLY_2, in `sync_read_with(&[1, 2], ..)` gives `[(1, Timeout), (2, Timeout)]`. ID 2's valid reply was taken in as ID 1's 'data'. The existing corruption test exempts positions 5..=7 for this reason. The spec edge case says: "Reply whose declared length exceeds the largest packet this build can hold: protocol error".

**Fix**: In p2.rs StatusParser, State::Instruction, when byte == STATUS, also reject LENs this reply cannot fit. At that point `remaining` = LEN - 1. If `self.remaining > 3 + self.out.len() + self.out.len() / 3 + 1` (error byte, 2 CRC bytes, data, worst-case stuffing), set `self.malformed = true; self.restart();`, the same as the existing `< 3` branch. Note that a well-formed reply that is larger than `out` will then give Malformed, not WrongLength. Update replies_from_another_id_or_of_another_size_are_rejected if it expects WrongLength for an oversized reply. Narrow the 5..=7 exemption in the corruption test, and add the sync_read test expecting [(1, Err(..)), (2, Ok([0x1F,0x08,0,0]))].

**Skeptic (confirmed)**: I reproduced it. Flipping bit 7 of LEN_H (byte 6) in READ_REPLY_1, followed by a valid READ_REPLY_2, in sync_read_with(&[1,2]) gives [(1, Timeout), (2, Timeout)]. The parser takes the LEN of about 32K at face value, swallows ID 2's valid reply as data, and the line only resyncs after the deadline. The existing corruption test skips positions 5..=7 for exactly this reason. The parser stays memory-safe (it writes through get_mut), but the spec edge case says a declared length the build cannot hold is a protocol error. Here it is a timeout, and the next actuator's reply is lost. The cost is real on a noisy bus, which is what User Story 3 is about.

### unbounded-len-swallows-following-replies (medium, protocol-compliance)

`src/protocol/p2.rs:239`: The P2 parser accepts any LEN up to 0xFFFF, even though the caller knows the exact expected data size. A single bit flip in one reply's LEN_H makes the parser swallow every following reply until the deadline. In `sync_read`, every later ID then also times out, each after a full timeout of its own. The spec edge case requires a protocol error instead.

**Evidence**: p2.rs:239 `self.remaining = usize::from(u16::from_le_bytes([self.len_l, byte]));` only rejects `< 3`. Spec 001 edge case: "Reply whose declared length exceeds the largest packet this build can hold: protocol error". Probe in a scratch copy: sync_read of ids [1,2] with READ_REPLY_1 (LEN_H ^= 0x80) followed by a valid READ_REPLY_2 gave `got=[(1, Err(Timeout{id:1})), (2, Err(Timeout{id:2}))] elapsed_us=20300`. Actuator 2's valid reply was lost.

**Fix**: In p2::StatusParser, when `State::Instruction` sees `STATUS`, reject a LEN larger than the reply the caller expects: `let body = 2 + self.out.len(); let max = body + body / 3 + 2; if self.remaining + 1 > max { self.malformed = true; self.restart(); }`. `remaining` has already been decremented for the instruction byte. On restart, hunting resumes on the following bytes, so the next real header is still found. Keep the check out of the LenH and Skip states so long non-status packets (echoes) are still skipped. Add the same bound to the P1 parser (LEN > out.len() + 2 → malformed, restart). Add a sync_read test with a flipped LEN_H followed by a valid reply.

**Skeptic (confirmed)**: I reproduced it in a scratch copy using the existing `sync_read_with` helper: ids [1,2], READ_REPLY_1 with byte 6 (LEN_H) XOR 0x80, then a valid READ_REPLY_2. The result was `[(1, Err(Timeout{id:1})), (2, Err(Timeout{id:2}))]`. The LenH branch (p2.rs:239-245) only rejects `< 3`, so the Data state consumes reply 2 as payload. The packet never completes, so the error is Timeout rather than a protocol error (`malformed` is never set), and actuator 2's valid reply is lost. One correction to the claim: under the streaming design the 'largest packet this build can hold' is effectively the LEN field limit, so the spec edge case is not literally violated by LEN 0x8008. The robustness problem (one corrupted LEN wipes out the replies after it and is reported as Timeout) is real.

### sync-read-late-earlier-reply (low, protocol-correctness)

`src/protocol/p2.rs:468`: In sync_read, a late reply from an ID that was already given a timeout is not skipped. It is handed to the next ID as `WrongId`, and that ID's own valid reply is left unread on the line.

**Evidence**: p2.rs:460-470: held only covers `status.id` matching a *later* pending ID. Any other ID falls into `Ok(status) => on_reply(id, check::<P2>(status, id, size_usize)..)`, which returns WrongId. Scratch test: ids [1, 2], both replies arrive at t=15ms with a 10ms timeout. Result: `[(1, Timeout), (2, Err(Protocol(WrongId { expected: Id(2), got: 1 })))]`, `unread=15`. ID 2's valid reply is left on the line and is only drained before the next exchange.

**Fix**: In P2::sync_read, keep a clone of the original `ids` iterator. For the current `id`, compute `deadline` once, then loop on `receive(link, &mut StatusParser::new(buf), deadline, Some(id))`. While the received status.id is one of the IDs already handled (`all.clone().take_while(|x| *x != id).any(|x| x.get() == status.id)`), discard it and receive again with a fresh parser and the same deadline. Only then apply the existing `held` / check / error arms. Add a test with both replies late: expect [(1, Timeout), (2, Ok(..))] and unread == 0.

**Skeptic (confirmed)**: I reproduced it. With ids [1,2], both replies arriving at t=15ms and a 10ms timeout, the result is [(1, Timeout), (2, Err(Protocol(WrongId { expected: Id(2), got: 1 })))] with unread=15 (all of READ_REPLY_2). ID 2's valid reply arrived inside ID 2's own deadline (10ms to 20ms) but was left on the line. The `held` arm only covers IDs later in the list, so a reply from an ID that already timed out goes to the WrongId path. G4 does not cover this case, so nothing makes it intentional.

### broadcast-ping-drops-error-byte (low, protocol-correctness)

`src/protocol/p2.rs:497`: broadcast_ping reports replies whose error byte is set, but `Pong` has no error field. An actuator in hardware alert shows up as a healthy pong, and the error byte is silently dropped. This contradicts FR-009 and contract G6.

**Evidence**: p2.rs:497 `if let (3, Ok(id)) = (status.len, Id::new(status.id)) { on_reply(pong(id, data)); }` never reads `status.error`, and `Pong { id, model_number, firmware }` cannot carry it. FR-009: "Every parsed status packet's error byte MUST be checked ... A set fault MUST be reported as a typed error". G6: "Every status packet's error byte is decoded".

**Fix**: Add `fault: Option<StatusReport>` to `Pong` (protocol.rs; update data-model.md and contracts/protocol-api.md). Fill it in `broadcast_ping` with `(status.error != 0).then(|| P2::report(status.error))`. Set it to None on unicast ping, which already returns Err(Status) on a non-zero byte. Add a test: a broadcast ping reply with error byte 0x80 gives a Pong with fault == Some(P2 { alert: true, code: None }). Or, if the architect wants to keep presence-only behaviour, record that as a deviation from FR-009 in the PR.

**Skeptic (confirmed)**: In p2.rs broadcast_ping, the code calls on_reply(pong(id, data)) whenever status.len == 3 and never looks at status.error. Pong has no field that could carry the error, so an actuator in hardware alert shows up as a healthy pong. The doc comment ('A reply whose error byte is set is still reported: the actuator is present') shows this was a choice. But it is not on the known-and-intentional list, and it goes against FR-009 ('Every parsed status packet's error byte MUST be checked ... reported as a typed error'), SRS FR-6.1 and contract G6. In practice the fault would probably show up on the EEPROM limit reads at setup, so the impact is low. It is still a direct spec deviation.

### p1-bit7-reports-no-error (low, protocol-correctness)

`src/error.rs:322`: A P1 error byte with only bit 7 set (unused per the e-Manual) still becomes a StatusError, because `check` tests `error != 0`. That error displays as "actuator N reported no error", and the raw byte is shown nowhere.

**Evidence**: protocol.rs:232 `if status.error != 0 { return Err(StatusError{..}) }`. P1Flags::iter only covers `P1Flag::ALL` (bits 0..=6), so for `P1Flags(0x80)` Display goes to `None => f.write_str("no error")` (error.rs:322). The e-Manual P1 page says "Bit 7 is unused".

**Fix**: In error.rs `impl fmt::Display for P1Flags`, after the known flags, add any bits outside them: `let unknown = self.0 & 0x80;`. If there are no known flags, write `unknown error bits 0x{unknown:02X}`. Otherwise append `, unknown error bits 0x..` when `unknown != 0`. Add a test that P1Flags(0x80) does not display as 'no error'.

**Skeptic (confirmed)**: check() returns Err for any non-zero byte. P1Flags::iter only covers P1Flag::ALL (bits 0..=6), so P1Flags(0x80) displays as 'no error' and the StatusError reads 'actuator 1 reported no error'. The e-Manual says P1 bit 7 is unused, so this only happens with odd firmware or corruption the checksum did not catch, which makes it low impact. One part of the claim is overstated: Debug still shows P1Flags(128), so the raw byte is not hidden everywhere. The misleading Display text is real and goes against T005's 'Display lists every reported condition'.

## Uncertain (needs a decision)

### status-error-discards-valid-data (medium, protocol-compliance)

`src/protocol.rs:232`: `check` turns any non-zero error byte into `Err(StatusError)` and drops data that was already received. On P2 the alert bit stays set until reboot, so once an actuator faults, every read fails. That includes Hardware Error Status (addr 70) and Present Temperature, so the bus can neither say which fault occurred nor read diagnostics, which FR-6.5 `clear_fault()` and FR-6.2 reporting need.

**Evidence**: protocol.rs:232-238 `if status.error != 0 { return Err(StatusError { id, report: P::report(status.error) }.into()); }` runs before the data is returned. Probe: P2::read(addr 70, 4 bytes) against a CRC-valid reply with error byte 0x80 and data [0x20,0,0,0] -> `Err(Status(StatusError { id: Id(1), report: P2 { alert: true, code: None } }))`, and the 0x20 (overload bit) is lost. The DynamixelSDK readRx2 copies `data_read` whenever `communication_result == COMM_SUCCESS`, whatever the error byte.

**Fix**: If the architect wants diagnostics: in `check`, validate the ID and length before the error byte. Document on `Exchange::read` that a `Status` error after a valid ID and length leaves `out` filled with the reply data. For `sync_read`, change the callback's payload so it can carry both, e.g. `Result<&[u8], Error>` plus `Option<&[u8]>` on StatusError, or a `(Option<StatusReport>, &[u8])` success variant.

**Skeptic (uncertain)**: I probed P2::read(addr 70, 4 bytes) against a CRC-valid reply with error byte 0x80 and data [0x20,0,0,0]. It returned `Err(Status(StatusError{alert:true, code:None}))`, but `out` was [32,0,0,0], so the claim that the data is dropped is false for unicast `read`. The parser fills `out` before `check` runs. That behaviour is undocumented, though, and `check` tests the error byte before the length, so `out` may be only partly filled. In `sync_read` the callback gets only `Err` and cannot reach `scratch`, so there the data really is lost. Returning an error on alert is what SRS FR-6.2 ('returns a typed hardware error from the call that received it') and contract G6 require. FR-6.5 still works: the alert makes clear_fault fail until the actuator is rebooted. No SRS item requires reporting which fault occurred, but the e-Manual tells users to check Hardware Error Status for the cause, and the current API cannot do that reliably. This is a real design gap that the architect should decide, not a clear defect.

### clock-missing-from-bus-signature (low, protocol-compliance)

`docs/srs/SRS.md:156`: Every exchange needs a `C: Clock`, and the SRS says the bus holds the clock, but FR-1.1 still fixes the bus type as `Bus<P, T, const N>` with no place for one. The bus module must either add a type parameter that contradicts FR-1.1 or erase the clock type.

**Evidence**: SRS.md:156 `Bus<P: Protocol, T: Transport, const N: usize = 32>`. SRS.md:136 and constitution.md:103 say "the bus polls ReadReady against its Clock". protocol.rs:57-59 `Link { transport: &'a mut T, clock: &'a mut C, ... }`, and every `Exchange` fn is generic over `C: Clock`. The contract says "No new type parameter is visible to users in this feature; Bus wiring is the bus feature."

**Fix**: Decide this before starting the bus module and record it in FR-1.1. For example `Bus<P, T, C = StdClock, const N>` under std; or make the clock part of the transport (`T: Transport + Clock`); or take the clock per call.

**Skeptic (uncertain)**: The inconsistency is real: FR-1.1 is 'Decided' as `Bus<P, T, const N>`, while 4.4, the glossary and the 2026-10-26 decision say the bus polls ReadReady against its Clock. The SRS also does not record where the clock lives. However, the contract explicitly leaves this to the bus feature ('No new type parameter is visible to users in this feature; Bus wiring is the bus feature'), so it is not a defect in the protocol module under review. The two are also not forced into conflict: `Clock` is implemented for any `FnMut() -> u64`, so the bus could store a `fn() -> u64` (StdClock can be a static origin under std) without a new type parameter. It is worth adding as an SRS open question before the bus module starts, but it is not a confirmed defect here.

## Refuted by the skeptic (kept for the record)

### broadcast-ping-window-too-short (high, protocol-compliance)

`src/protocol/p2.rs:492`: `broadcast_ping` collects replies only for one per-reply bus timeout (`link.deadline()`). With the FR-1.4 default of 10 ms, autoscan (FR-2.1) will miss actuators whose replies come later. ROBOTIS's own SDK waits about 3 ms per possible ID plus 16 ms plus transfer time.

**Evidence**: p2.rs:492 `let deadline = link.deadline();` (one `timeout` for all replies). DynamixelSDK protocol2_packet_handler.c broadcastPing2 sets `setPacketTimeoutMSec(port_num, ((double)wait_length * tx_time_per_byte) + (3.0 * (double)MAX_ID) + 16.0)`, about 770 ms plus wire time. The doc comment at p2.rs:479 admits the e-Manual does not specify reply timing. SRS FR-1.4 sets the default status timeout to 10 ms.

**Skeptic (refuted)**: broadcast_ping uses the caller's `Link.timeout` as one window, which is exactly what contract G5 and data-model.md say ('Broadcast ping: one window, all replies inside it collected'). The doc comment at p2.rs:476 already says it collects answers 'within one timeout'. The e-Manual (I re-fetched protocol2 #ping) gives no reply order or timing for broadcast ping. The finding's only timing source is DynamixelSDK, and SRS 4.4 rules that out as a source. The 10 ms default is an FR-1.4 bus-level choice that is still marked Proposed, and the bus can build a Link with a longer timeout for autoscan. So the protocol module is not defective. The open question of what window autoscan should use belongs in the bus spec, ideally measured on hardware (NFR-5).

### sync-read-cannot-stop-early (medium, protocol-compliance)

`src/protocol/p2.rs:428`: The `sync_read` callback returns `()`, so a strict read (FR-4.6), which already knows the call has failed after the first error, still waits a full timeout for every remaining silent ID. Also, on a transport I/O error the remaining IDs never get their callback, despite the documented "exactly once per ID".

**Evidence**: p2.rs:428 `F: FnMut(Id, Result<&[u8], Error>)`. Probe: sync_read over 32 silent IDs with a 10 ms timeout -> `callbacks=32 elapsed_us=323300`, i.e. 323 ms for a read the bus would fail after 10 ms. p2.rs:469 `Err(err @ Error::Transport(TransportError::Io(_))) => return Err(err)` skips the callbacks for the remaining IDs, while the doc at p2.rs:412 says `on_reply` is called exactly once per ID.

**Skeptic (refuted)**: FR-4.6 only says a strict read fails the whole call. It does not require stopping at the first failure. The proposed early stop is also unsafe. The e-Manual says Sync Read replies come back 'in order, according to input ID', so later actuators may still be transmitting after the master stops listening. `drain` only discards bytes that are already waiting (it loops on `read_ready`), so a reply still on its way can collide on the half-duplex line with the next instruction or its status. The 323 ms figure is for 32 all-silent IDs, a pathological case. The 'exactly once per ID' doc nit is minor: the same doc comment (p2.rs:416-417) and G4 both say Err is returned on transport failure, and that already implies the remaining callbacks are skipped. A one-line doc clarification ('callbacks stop if the transport fails') would be nice to have, but it is not a defect.
